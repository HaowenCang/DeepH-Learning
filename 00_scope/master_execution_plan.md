# DeepH 系统学习与研究主执行计划

## 1. 文档目的与约束

本文件是 DeepH 系统学习项目的主执行基线，用于约束教材编写、理论推导、代码练习、软件复现和研究改进的顺序与验收标准。后续工作应以本文件、`learning_route.md`、`prerequisite_map.md` 和阶段审计记录为共同依据。

项目采用可核验门槛而非固定周数推进。M3—M7 采用“材料建设模式”：任何阶段只有在教材、推导、例题、练习与参考解答、代码、自动检查、失败样例和独立审计同时满足要求后才能标记为完成；不再要求学习者本人提交闭卷作答、口头解释或逐阶段自测。模式变更只改变证据载体，不降低知识范围、公式条件、来源边界或验证强度。不得因为时间不足而省略矩阵约定、数据血缘、对称性测试或下游物理量验证。

## 2. 统一状态与完成定义

进度只使用以下状态：

| 状态 | 含义 |
|---|---|
| `PLANNED` | 已进入计划，但前置条件尚未满足 |
| `READY` | 前置条件满足，可以开始 |
| `IN_PROGRESS` | 已有实际工作，但尚未达到门槛 |
| `BLOCKED` | 存在必须由资料、决策、环境或外部输入解决的阻塞项 |
| `REVIEW` | 交付物已经形成，正在审计 |
| `AWAITING_USER_DECISION` | 候选方案和证据已经提交，等待用户冻结会实质改变后续路线的选择 |
| `AWAITING_EXECUTION_AUTHORIZATION` | 方案已经冻结，但会产生外部安装、下载、计算或正式数据变更的下一阶段尚未获得执行授权 |
| `COMPLETED` | 交付物、验证与审计全部通过 |

“完成”必须同时具备四类证据：

1. 可定位的交付文件；
2. 可重复的推导、测试或检查结果；
3. 自学检查题、参考解答、常见错误与能力—材料覆盖映射；
4. `08_audits/` 中明确给出通过结论的门控记录。

不得使用“已阅读”“代码能运行”“训练损失下降”或主观完成百分比代替上述证据。

## 11. 阶段 F：最小 DeepH 复现闭环

复现链为：

```text
固定数据
→ 校验和与数据血缘
→ 预处理
→ 训练
→ 推理
→ 实空间矩阵检查
→ k 空间重建
→ 广义本征求解
→ 物理量评价
→ 分布外与成本分析
```

最低自动检查包括：

- 轨道块尺寸、单位、索引和稀疏模式；
- \(H=H^\dagger\) 及晶格平移关系；
- \(S\succ0\) 与条件数；
- 适用的旋转、反演或时间反演残差；
- 全矩阵和轨道分辨误差；
- 全能带与费米能窗误差；
- 带隙、带宽、DOS、简并和本征态相关指标；
- 结构分组的分布内与分布外结果；
- 训练、推理、矩阵组装、对角化和后处理成本；
- 已知失败样例。

只有矩阵、对称性和下游物理量验证同时通过，才能认定 M9 完成。

### 12.2 研究设计

每个候选改进采用：

\[
\text{可观察缺陷}
\rightarrow\text{机制假设}
\rightarrow\text{最小代码改动}
\rightarrow\text{控制实验}
\rightarrow\text{消融与反例}
\rightarrow\text{失败判据}.
\]

首个改进应保持可撤销、可单独消融，并在固定数据、训练预算和评价脚本下与基线比较。结果应同时报告多随机种子、统计不确定性、物理重要性和计算代价。

## 13. 教材编写顺序

首批教学单元依次为：

1. 第 1 章：DeepH 所求解的问题；
2. 第 2—4、9 章：量子表示、非正交基与周期 Hamiltonian；
3. 第 5—8、10 章：DFT、SCF、基组与局域性；
4. 第 11—14 章：监督学习、周期图与普通 MPNN；
5. 第 15—20 章：群表示与等变网络；
6. 第 21—28 章：原始 DeepH 方法与实现；
7. 第 29—33 章：方法扩展；
8. 第 34—42 章：数据、验证、比较、研究设计与可复现性。

可并行推进基础线性代数、Python 数值练习、量子力学和监督学习；不得跳过阶段 B 直接解释 DeepH 数据矩阵，不得跳过普通 MPNN 和群表示直接进入显式等变网络，不得跳过版本与数据冻结直接执行正式复现。

## 14. 进度管理规则

### 14.1 每次工作开始前

- 从 `08_audits/progress_tracker.md` 选择一个 `READY` 或 `IN_PROGRESS` 任务；
- 核查前置条件和允许修改的文件范围；
- 明确本次交付物、验证命令和停止条件；
- 若任务涉及随时间变化的软件或论文状态，先刷新来源台账。
- M3—M7 的普通内容组织、Python 用户态依赖、合成数据和可逆实现细节由 Codex 自主决定并记录；只有无法从现有资料解决且不同选择会实质改变路线时才询问用户。

### 14.2 每次工作结束时

- 更新任务状态、最后更新时间、产物路径和验证结果；
- 记录尚未解决的问题及其证据状态；
- 将新决策写入 `decisions.md`；
- 将阶段门控结果写入 `08_audits/`；
- 明确下一项唯一主任务；
- 不得把未审计产物标为 `COMPLETED`。

### 14.3 阻塞处理

阻塞项必须记录：问题、影响范围、所需证据、负责人或外部输入、允许继续的非阻塞工作。无法确定软件接口、数据语义或矩阵约定时，应停止依赖该结论的工作，而不是作隐含假设。

### 14.4 变更控制

影响阶段顺序、教材范围、软件对象、数据来源、标签定义、验证标准或复现基线的变更必须记录在 `decisions.md`，说明采用依据、拒绝方案、影响文件和重新评估条件。状态、版本和来源更新不得静默覆盖旧结论。
